## 这轮实际验证了什么

验证器只复用现有 provider seam：

```text
raw intent + 一次普通语言补充
→ synthesizeTurn
→ synthesizeAgreement
→ proposed smallest complete outcome
```

没有修改 WorkUnit schema、AAOP Core、Harness adapter，也没有增加 Memory、
Agent、Workflow 或状态系统。`final_outcome` 是待确认的目标，不是已经执行并
独立验证的 Outcome Truth。

## 人工评价标准

逐案按五项审阅，不评价文案漂亮程度：

1. 是否抓住真正问题？
2. 是否理解隐含约束？
3. 是否过度设计？
4. 是否替用户做了不该做的决定？
5. 是否提出了正确需要确认的问题？

出现失败先记录原因，再归类：

- A：模型理解能力 / provider / model；
- B：synthesis contract 不足；
- C：用户输入仍需更多上下文；
- D：Outcome schema 无法承载。

不得先改 prompt 来掩盖失败。

## 三个验收问题

### 1. 真实 LLM 是否比 deterministic provider 更接近人的真实意图？

**目前可以给出“语义上更接近，但还不能作为产品通过”。** 真实 provider 在
9/15 次成功输出中，能把问题和约束具体化（例如“不想维护”“孩子自己照着做”、
“先从常做几道开始”）；deterministic fixture 只机械回显首句并给出通用最小版本。
但 6/15 次没有满足 JSON contract，且成功输出多次擅自加入“3 件事”“3 天”、
“冰箱/家庭群/共享相册”等未确认决定。因此这是有方向性的真实证据，不是通过证明。

### 2. 当前 Outcome schema 是否足够承载真实人的模糊目标？

**当前结构可以承载建议，但不足以审计 Intent Fidelity：**
`IdeaSynthesis` 没有独立的“隐含约束”或“待确认问题”字段，
`RoundAgreement` 也没有独立的 unresolved ambiguity / correction 记录字段。
真实输出中的未授权细节目前只能靠人工从自由文本中发现；这些缺口先只记录，
本轮不扩展 schema。

### 3. 下一步进入 A、B 还是 C？

**选择 C：先增强 Intent Intelligence，再考虑 B。** 真实 provider 已能抓住核心
问题，但 40% 的尝试无法满足 synthesis contract，且可用输出仍反复擅自填入未确认
细节；这不是继续接 Harness transport 能解决的执行问题。增强必须先由人工审阅
确认失败边界，仍不得直接扩展 schema 或堆新系统。
